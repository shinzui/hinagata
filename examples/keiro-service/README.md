# Keiro consumer and isolated service suites

From the Hinagata repository root, run `nix develop -c just example-keiro`. The command builds the test-only service and migration executable, starts a disposable PostgreSQL socket cluster, creates separate setup and application roles, and runs the pinned `mori://shinzui/hurl-workbench` revision `a29d26ad5e90aa762de88be18f06fddf67b6d02f`.

The migration executable composes Kiroku, Keiro, and application migrations in one pg-migrate plan. Its `up` command runs the full plan; `verify` checks the complete ledger and the application-owned live schema separately. The script hashes the migration executable for both Hinagata hook revisions, so changed embedded SQL or a changed runtime cohort causes a new baseline. The checked-in YAML leaves the machine-specific socket, paths, roles, and executable locations to explicit Settei environment bindings supplied by the script.

`reference-seed` is the baseline fixture: IDs 1 and 2, codes `alpha` and `beta`. `service-scenario` includes that same fixture and adds ID 3, `gamma`. Hinagata confirms the overlap against captured fixture identity and loads only the scenario suffix on each clone. The `generated-id` suite then inserts a row without an explicit ID and observes ID 4.

The ordinary `default` suite contains independent read-only health and reference requests. It runs twice on different ports and leases. The opt-in `counter-write` suite sends a command through Keiro's public `runCommand` API and reads the resulting stream through Kiroku's public store API. `generated-id` is also opt-in; both write suites require workbench's `--allow-mutating`. Every request checks its status, and every body-bearing response checks JSON media type and stable semantics. The example tests a missing reference and an invalid counter ID; the driver also proves the application role receives SQLSTATE 42501 when it attempts a privileged schema write. Runtime tables are populated only by the released migration and command/store APIs.

The service wrapper maps Hinagata's application `PG*` lease variables to service-owned `SERVICE_*` Settei settings before startup. Workbench owns readiness and service shutdown. One workbench suite uses one clone, so separate `db with` invocations provide suite isolation. The script confirms released leases after normal completion, after an unready service fails to start, and after interrupting the full workbench/service scope. The test-only `/hold` route keeps the cancellation suite active long enough to observe process-group shutdown. The script prints end-to-end elapsed milliseconds for each normal workbench suite.
