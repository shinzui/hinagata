# Prior art and design lessons

Reviewed 2026-09-26 for design inspiration. This is source/documentation research, not a comparative benchmark or a claim that Hinagata is implemented. The [spec](../initial-spec.md) and [MasterPlan](../masterplans/1-build-hinagata-for-fast-postgresql-fixtures-and-isolated-microservice-tests.md) incorporate the decisions below.

The pgtestdb tests also cover a migration using concurrent index creation while other callers wait. This reinforces keeping Hinagata's coordination sessions in the maintenance database and leaving transaction boundaries inside migration hooks to the application's migration tool. Fixture transactions remain a separate contract.

Other primary documentation reviewed:

- [Testcontainers Go PostgreSQL snapshots](https://golang.testcontainers.org/modules/postgres/#using-snapshots): prepare migrated state once and restore for subsequent tests. Its native driver path avoids the slower container-exec fallback. This supports Hinagata's native sessions and an explicit maintenance target; it does not justify requiring containers.
- [Respawn](https://github.com/jbogard/Respawn), canonical project `mori://jbogard/Respawn`, project-relative `README.md` (artifact-level URI pending): computes and caches foreign-key-aware table deletion order. Separate preparation from repetition, but defer in-place reset: it has a different isolation/ownership contract from new clones.
- [DbUnit components](https://www.dbunit.org/components.html): composable datasets and forward-only streaming support reusable fixture composition with bounded memory. Whole-database comparison and XML import are separate features, not first-release requirements.
- [DBLab Engine](https://v2.postgres.ai/docs/database-lab): filesystem/storage copy-on-write cloning can serve production-scale datasets, with an additional server and storage infrastructure. PostgreSQL template copies on an existing service cluster do not offer the same scaling guarantee.
- [PostgreSQL bulk-loading guidance](https://www.postgresql.org/docs/18/populate.html): COPY and subsequent ANALYZE matter to load and query performance. [CREATE DATABASE](https://www.postgresql.org/docs/18/sql-createdatabase.html) documents template restrictions and clone strategies. Any strategy experiment must use the actual supported PostgreSQL/storage environment.

## Adopt in the initial design

1. **Prepare once, use repeatedly.** Retain validated immutable plans and opaque baseline references across a suite. Recheck database identity/sealed state on acquisition without rereading all fixture files. Disk-cache imports still require integrity validation. Publish only complete generations; expose failed construction and cancellable, deadline-bound waiting.
2. **Make base/scenario composition precise.** Build a combined graph with base roots first, then scenario roots. The base closure is a prefix; execute only the remaining fixtures on its fresh clone. A shared name must have identical captured definition/content identity, including its dependencies. Refuse mismatches before allocation. This optimization requires a verified Hinagata baseline, never a guessed set of rows in a borrowed database.
3. **Explain reuse.** Keep a versioned, non-secret fingerprint manifest. Report reuse/build reason, changed component categories against a selected previous generation, and stage timings. When there is no comparable prior generation, report that rather than inventing a diff. Include role/ownership and hook identities where they affect prepared state. Do not put credentials, including password-derived digests, into cache identities.
4. **Use realistic roles.** Configure administration, setup, and application access explicitly. Bootstrap creates roles; Hinagata does not. Handoff uses application credentials, and permission tests verify both permitted and forbidden operations. Application role identity and declared grants/settings are configuration, not secrets.
5. **Bound demand and surface outcomes.** A suite-scoped manager bounds concurrent setup, active leases, and pending requests. Acquisition consumes one deadline across queueing, lock waits, and setup. Document the manager's process-local limit and application pool headroom; this is not a global cluster scheduler. A caller-provided outcome classifier recognizes failures returned as values, alongside exception/cancellation handling, so preservation works without depending on a particular test framework.
6. **Measure the repeated path honestly.** Prove that an unchanged large baseline does not recopy input CSV during each test. Measure allocation wait, database work, service startup, and cleanup independently. Include realistic indexes/constraints, explicit sequence handling, and declared ANALYZE policy so fast loading does not hide slow or incorrect service behavior.

These are Hinagata design judgments informed by the evidence, not claims that every reviewed library provides all these guarantees.

## Defer or reject

Precreated spare clones merit a bounded experiment only if cloning dominates measured setup. Report preparation cost, disk use, cleanup, connection count, and acquisition p95; do not publish a warmed acquisition number as total cost. A pool is not an initial public API or daemon requirement. Any later pool must preserve exclusive leases, discard used clones, and never infer safe reclamation merely from an idle connection count or elapsed time. IntegreSQL's source has a direct return-without-cleaning operation; Hinagata will not expose that shortcut.

Defer filesystem snapshots, dump portability, automatic table reset, expected-dataset comparison, and a generalized fixture generator. Keep constraints/triggers and normal durability enabled. Published upstream timings are not Hinagata performance evidence. The existing five child plans are sufficient; the changes tighten their contracts and acceptance rather than add another subsystem.
