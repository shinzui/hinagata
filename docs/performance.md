# Fixture and clone performance

Run `nix develop -c just bench-fixtures` from the repository root. It builds the CLI and benchmark executables, starts an owned disposable socket-only PostgreSQL cluster, generates deterministic fixture inputs in a temporary directory, then writes `bench/results/<UTC timestamp>/results.json` and `summary.txt`. That ignored JSON contains every sample, SHA-256 input checksum, phase timing, process RSS, GHC RTS counters, checkpoint counters, connection observations, and gate verdict; the text file repeats the printed human summary. The driver fails a full 30-small/5-bulk run when a release target is missed. Short smoke runs can set `BENCH_REPS_SMALL`, `BENCH_REPS_BULK`, and `BENCH_ROWS_BULK`; they are not release evidence.

Reference run: 2026-10-02 16:10 UTC on macOS 26.7, Apple M1 Max, APFS, GHC 9.12.4 (`-O1`; direct-load benchmark `+RTS -s -RTS`), PostgreSQL server/client 18.6. The disposable cluster used default durability and constraints, a Unix socket, and trust authentication. Filesystem caches were warmed by unreported first samples and were not flushed. Bulk methods run serially; the separate concurrency probe uses 1/4/8 callers and a four-worker manager cap. PostgreSQL server memory is separate from the process RSS and GHC RTS figures below. The data partition had 621 GiB free. No `ANALYZE` step runs in these fixture cases, so the numbers do not include statistics collection or subsequent service-query latency.

| --- | ---: | ---: | ---: | ---: | --- |
| 100-row warm scenario, full CLI lease scope | 184.8 ms | 195.8 ms | — | 30 | <250 ms median, <500 ms p95: pass |
| 1,000-row warm scenario, full CLI lease scope | 193.9 ms | 244.3 ms | — | 30 | <250 ms median, <500 ms p95: pass |
| 100,000-row CSV COPY phase | 79 ms | 84 ms | 83.6 ms | 5 each | 0.94× `psql`: pass |
| 1,000,000-row CSV COPY phase | 895 ms | 938 ms | 891.0 ms | 5 each | 1.00× `psql`: pass |

Each small scenario contains generated SQL for exactly 100 or 1,000 deterministic rows. A sealed schema baseline is prepared once; two warmups precede 30 fresh `db with -- true` scopes per size. The outer monotonic time includes CLI startup, scenario capture, clone allocation, a trivial child, and release. Their median clone phases were 45/49 ms and scenario SQL load phases 2/4 ms. Five full schema-baseline rebuild-plus-scenario runs per size took 446/458 ms median, about 2.4× the corresponding warm scope. The separate cold and warm `db prepare` calls include bundle capture and catalog work and are not isolated compiler timings.

For bulk COPY, both methods use `id integer PRIMARY KEY, payload text NOT NULL`, the same generated CSV bytes, ordinary WAL durability, and one transaction/session that creates the table and copies rows. Hinagata's measured COPY phase includes its streamed digest check and server completion, while `psql`'s `\timing` measures the `\copy` command. Separate outer times include each executable's startup and setup. One warmup precedes five measurements per method and size. The 100k source is 1,388,895 bytes with SHA-256 `03fff84f2f159fe6d85ad403d0d659f7fc48bfab6a1e3ae12e91c222fe649579`; the 1m source is 14,888,896 bytes with SHA-256 `36be8ada04e2d0fda64db5779c7212c8aa27841f34151bcdd53caaac6a606570`. The driver checks Hinagata's transferred CSV byte count against the `psql` input. Median COPY throughput was about 1.27 million rows/s at 100k and 1.12 million rows/s at 1m. Five-sample p95 is a descriptive maximum-near-tail, not a stable tail estimate.

The 100k/1m Hinagata process median RSS was 28,688,384 bytes at both sizes: no observed growth against the 64 MiB incremental target. GHC maximum residency was about 221 KiB at both sizes. Median RTS allocation for the whole benchmark process was 128 MB/1.36 GB; this includes deterministic CSV generation and bundle compilation, so it is not a COPY-only allocation count. Before the per-chunk libpq flush correction, the same 1m workload had 44.7 MB process RSS and 1.55 s COPY median versus 0.93 s `psql`. PostgreSQL's [nonblocking libpq contract](https://www.postgresql.org/docs/18/libpq-async.html) explains the queued client bytes: a successful `PQputCopyData` still needs `PQflush`. The corrected loader flushes each bounded 64 KiB chunk.

The same million-row CSV was also loaded once into a sealed base and cloned with both PostgreSQL strategies. The cold bundle-plan call took 113 ms, cold baseline preparation 1,461 ms, and warm reuse 269 ms. Five measured scopes followed one warmup per strategy. Median `WAL_LOG` clone phase was 364 ms (full CLI scope 909 ms); `FILE_COPY` was 91 ms (full scope 633 ms). Five full rebuilds after migration-revision changes took 1,579 ms median, about 1.7× the `WAL_LOG` full scope and 2.5× the `FILE_COPY` full scope. The unchanged base produced a 1–2 ms scenario-load phase after suffix-only bundle verification, compared with about 76 ms when each lease rehashed its included million-row base. PostgreSQL's [CREATE DATABASE reference](https://www.postgresql.org/docs/18/sql-createdatabase.html) says `FILE_COPY` forces checkpoints before and after a clone. The measured `pg_stat_checkpointer` requested/completed counter rose by 3 for each `FILE_COPY` scope versus 1 for each `WAL_LOG` scope, including the common release work. `WAL_LOG` remains the default because the extra checkpoint cost can affect unrelated workloads.

The manager probe reused one prepared million-row baseline, capped setup at four workers and active leases at eight, and held one application connection per callback. Each concurrency level had one warmup and three measured batches. `pg_stat_activity` was sampled during each batch; the maximum connection count excludes the observer but includes PostgreSQL background processes, maintenance/guard sessions, and those application connections.

| Concurrent leases | Median throughput | Median slowest request per batch | Peak observed `CREATE DATABASE` | Peak observed connections |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 2.18 leases/s | 459 ms | 1 | 11 |
| 4 | 2.29 leases/s | 1,745 ms | 4 | 16 |
| 8 | 2.15 leases/s | 3,713 ms | 4 | 21 |

At eight callers, four concurrent `CREATE DATABASE` statements were observed while four others waited for the configured setup cap; 12 of 24 per-lease queue-wait observations were nonzero. More demand increased the tail without increasing clone overlap past the cap. Three batches are useful for this capacity comparison but insufficient for a stable p95. The local `withManager` route avoids a new CLI process for each lease; the small and spare probes above measure fresh CLI invocations separately.

A bounded four-spare experiment used one-shot detached, owned clones; no used clone was recycled. Twelve on-demand acquisitions at concurrency four reached an application `SELECT 1` in 1,976 ms median / 2,611 ms nearest-rank p95. Four precreated spares reached the same query in 16/24 ms, but preparing them cost 2,879 ms, replenishing them cost 1,970 ms, and holding them used 299,227,900 bytes of database storage. Peak observed connections were 13 in both phases. The latency benefit is real, but it shifts clone work and storage ahead of demand and requires ownership, cancellation, replenishment, and crash semantics absent from the first-release API. The decision is to defer a spare pool.

The real Keiro/workbench example separately measured complete `db with` scopes including service startup, HTTP readiness, Hurl assertions, shutdown, and lease release. Five repeated concurrent two-service runs passed with distinct `gamma`/`delta` seed assertions; the last measured 3.89/3.91 s for the two read suites, 3.40 s for command/read, and 3.51 s for generated-ID write/read. These are end-to-end observations, not service tail estimates. Its readiness-failure and cancellation cases also released their owned clones. The separate PostgreSQL integration fixture exercises an explicit COPY-then-`ANALYZE` sequence, with `copyMs` and `sqlMs` reported separately; the release benchmark's CSV cases intentionally omit analysis.

The three numeric release targets pass on this reference machine. The archive-only build/test/Haddock gate, PostgreSQL correctness suite, and Keiro service proof pass separately; no cross-machine speed claim is inferred from these results.
